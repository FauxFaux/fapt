Summary

Master the gbp pq command.

The gbp pq command is used to generate a patch queue (a collection of patches for the upstream source code, located in debian/patches/) from Git commits.

Prerequisite knowledge for using gbp


Before using gbp, as prerequisite knowledge for Debian packages, there is the philosophy regarding Debian source code and two problems that package maintainers should be aware of.

In the Debian Project, Debian Packages are created by turning existing software into Deb packages.
Basically, a tarball of the software suite released by the upstream is often used.

In a Debian Package, when packaging, the content released by the upstream is strictly separated from the set of patches that modify the upstream source code to create the Debian package. This is to audit the patches and separate the responsibilities of the upstream and the package maintainer.

The patch management system for this is quilt. You can see that "debian/source/format" looks like the following when you examine a Debian package.

cat debian/source/format 
3.0 (quilt)

Regarding individual patches, there is a guideline called DEP-3: Patch Tagging Guidelines. I was mindful of this when creating patches with quilt or dpkg-source --commit.

When you run gbp pq import and create commits in the patch-queue/working-branch, the program does not automatically add this information, so you will likely want to record similar information yourself.

However, if you use gbp, using raw quilt, dquilt, or dpkg-source --commit is fine only for those who can fix things even if they shoot themselves in the foot; basically, "mixing them is dangerous."
The reason I struggled with xfireworks this time was that I used dpkg-source --commit without understanding gbp pq.

Branches you should know in gbp

  • pristine-tar branch
  • upstream branch
  • Working branch for package creation.
    • If working only on the development version of Debian, specify main or master.
    • When providing packages for multiple distributions or for backports in addition to the development version of Debian, use different branches.

In addition to these three branches, you need to be aware of a total of four branches, including the "patch-queue/working-branch," which is created by gbp pq import and eventually deleted by gbp pq export.

What does gbp pq do?

To manage a Debian package, you need to create patches in debian/patches/. gbp pq import creates a "patch-queue" branch, and you modify the upstream source code in the patch-queue/working-branch. Following Git conventions, write a summary on the first line, leave the second line blank, and provide details starting from the third line. The content should follow the DEP-3: Patch Tagging Guidelines mentioned above. This information is not automatically generated by the program. The maintainer must include the necessary information in the commit message.

With gbp pq export, a quilt-format patch is generated in debian/patches/ for each commit in the patch-queue, using the first line as the filename. If you don't need to check the contents of the patch-queue (or if you are prone to forgetting to commit :-)), using gbp pq export --commit might be a good idea.

Also, if the --drop option is used, the patch-queue branch will be deleted.

In this state, running gbp buildpackage will apply the contents of debian/patches/ before the build process starts.

Commonly used gbp pq commands

The following section generally applies when you are modifying the upstream source code. If the upstream has released a new version, please read the section on handling new upstream versions with gbp.

gbp pq import --force --time-machine=10

The --force option, as described below, overwrites the patch-queue branch with the current contents of debian/patches/, even if the branch already exists.

In case of import, import even if the patch-queue branch already exists and overwrite its content with debian/patches.

The --time-machine=NUM option has the following meaning:

--time-machine=NUM
When importing a patch queue fails, go back commit-by-commit on the current branch to check if the patch-queue applies there.
Do this at most NUM times. This can be useful if the patch-queue doesn't apply to the current branch HEAD anymore,
e.g. after importing a new upstream version.

If the patch-queue import fails, it goes back commit-by-commit on the current branch to check if the patch-queue can be applied. You specify the number of times (commits) to go back. This is useful when the patch-queue can no longer be applied to the HEAD of the current branch, such as after importing a new upstream version.

gbp pq export --drop --commit

--[no-]drop

Whether to automatically drop (delete) the patch queue branch after a successful export

When used with gbp pq export, the patch-queue branch will be deleted after a successful export. If not specified, the patch-queue branch will not be deleted.

--commit

In case of export, commit debian/patches the changes to Git after exporting the patches.

When specified with gbp pq export, it will git commit the changes to debian/patches after exporting the patches.

Normally, you would need to do the following manually:

git add debian/patches
git commit

This option eliminates the need for the above and makes the operation easier.

gbp dch --release

If you are properly creating commits in the patch-queue, you can easily create the changelog by transferring the summary from the first line to debian/changelog.

Handling New Upstream Versions with gbp

  • If debian/watch is set, obtain the new release (such as a tarball) using uscan.
  • Import the obtained tarball with gbp import. If you make a mistake here, the pristine-tar delta management may fail, leading to a problematic situation where the content doesn't match the original tarball. It's best to research starting with gbp import-orig --uscan before proceeding.
  • Once the import is successful, verify whether existing patches (those in debian/patches/) are still needed for the new release and if they can be applied correctly.
  • This is where gbp pq rebase comes into play.
  • Use gbp pq drop for unnecessary patches, keep the necessary ones, and if necessary, rewrite and commit to organize the patches to be exported to debian/patches/.
  • Once the work is complete, run gbp pq export to generate patches from the commits.
  • If files under the debian directory need modification, work and commit on the branch specified by --debian-branch=. Regarding debian/changelog, the gbp dch --release command can generate a changelog template from the commits.
  • Assuming you have passed local builds and tests, push to the salsa.debian.org repository and run it through the CI provided by the salsa.debian.org CI team.
  • If the results are satisfactory, perform a source-only upload using dput or a similar tool.

Overview of gbp pq rebase

  1. Handling new upstream versions
    When a new version of the upstream is released, and you need to reapply the existing Debian patch set to the new base.

Example: Applying patches created for libfoo 1.2.0 to libfoo 1.3.0.

  1. Resolving patch conflicts
    Resolving conflicts that occur between upstream changes and Debian patches.

Reapplying patches while manually resolving conflicts.

  1. Organizing patch sets
    When reordering or merging patches is necessary.

Deleting unnecessary patches or adjusting dependencies between patches.

Example

gbp pq rebase
gbp:info: No pq branch found, importing patches
gbp:info: Trying to apply patches at '9e1b621a05637b260c349b766cc935ac53889bce'
gbp:info: 8 patches listed in 'debian/patches/series' imported on 'patch-queue/master'
gbp:info: Switching to 'patch-queue/master'
Current branch patch-queue/master is up to date.

When you run the gbp pq rebase command, you are moved to the patch-queue/working-branch. Here, you can use Git commands or an editor to create or drop intended patches.
If necessary, you can also use the gbp pq export command to write the patches out to debian/patches/. If you are not writing them out, you can move between branches using gbp pq switch.

gbp pq rebase is similar to git rebase in that it stops at the point of failure, allowing you to rewrite the code or settings, create a commit, and then proceed to the next patch, thereby keeping the scope of the problem small.
Its options are also the same as Git, such as --continue, --abort, and --skip, making it easy to understand. If a problem occurs and you create a commit that fixes it, use --continue; if you determine it's an unnecessary patch, use --skip; and if you want to abort and investigate elsewhere before returning, specify --abort.

Use this when you want to keep the patch order and content healthy in response to upstream changes.

Comparison with Alternatives

  • gbp pq apply: Simply applies patches only.
  • gbp pq rebase: Used when conflict resolution or patch reorganization is required.
